# セキュリティ

## 大事にすること（優先順）

上のものほど優先する。両立しないときは、上を守る方を選ぶ。

1. **秘密投票** — 誰が誰に投票したかを、運用者を含めて誰も結び付けられないこと。voter_id と candidate_id を、同じレコード・ログ・
   メトリクス・エラーに含めない（原則1）。票に入れるのは UUIDv4 の `ballot_id`（時刻を含まない。原則2）と、分に丸めた時刻（原則3）だけ。
   再投票の仮名 slot だけは票と一緒に記録するが、鍵は締切の手続きで破棄する。前回の投票内容は画面にも API にも返さない。
   投票期間中は、公開 API から候補者別の票や集計を見せない設定にできる（`chain.reveal_ballots`。原則14）。
2. **改ざんの検知** — 封印後の票の書き換え・削除・追加を、誰でも検出できること。ブロックはバイナリ正規化の SHA-256 でつながり
   （原則4）、ed25519 で署名され、アンカーが全シャードをまとめる。ジェネシスには選挙定義のハッシュが入る（ADR 0025）。
   `verifier verify` は公開 API と手元の選挙データ（seed）だけで検証でき、`tally` は検証と投票済み記録との突合に成功したときだけ集計する。
3. **鍵の管理** — 署名鍵・セッション用シークレット・再投票の鍵・管理用トークンを、設定ファイルや git に置かない（下の「[秘密情報](#秘密情報)」）。
4. **認証情報の保護** — パスワードは Argon2id のハッシュだけを保存し、平文は DB にもログにも残さない。ログインの失敗は、ID が無いのか
   パスワードが違うのかを、応答内容でも応答時間でも区別させない（同じ 401・同じ文言・存在しない ID でもダミーのハッシュで照合。原則15）。
5. **管理操作の保護** — 選挙状態の変更は、公開用のポートとは別の管理用リスナー（`admin.bind`）に、トークンつきでだけ受け付ける。
   外部に出さない（[architecture-scaling.md](architecture-scaling.md#管理用のポート)）。変更はすべて `election_audit` に残る。
6. **ログに個人情報を残さない** — 投票者 ID・ログイン ID・パスワード・再投票の鍵をログに出さない（確認スイートがログを検査する）。
7. **マイナンバーを保持しない** — ログインの `my_number` は受け取って破棄する（保存もログ出力もしない。原則7）。

## 秘密情報

すべて、設定ファイルには書けない（書くと起動時にエラー）。`secrets/`（git 管理外。1 ファイル 1 値。権限 0600 にする）か環境変数で渡す。

| 秘密情報 | 使うもの | 保管場所 | ローテーション | 破棄 |
|---|---|---|---|---|
| セッション用シークレット `session.secret`（16 バイト以上） | api（全台で同じ値） | `secrets/session_secret` / `APP__SESSION__SECRET` | いつでも。全 api を同じ値で再起動する。発行済みのセッションはすべて無効になり、有権者は再ログインが必要（投票済みの記録は残る）。サーバ側でセッションを失効させる仕組みは無いので、漏れたら直ちに変える | 選挙の終了後に消す |
| 署名鍵の種 `sealer.signing_seed`（64 桁の hex） | sealer（全台で同じ値） | `secrets/sealer_signing_seed` / `APP__SEALER__SIGNING_SEED` | 選挙の途中では変えられない（DB に最初に登録した公開鍵と違う鍵の sealer は起動を拒否される）。選挙ごとに新しく作る。公開鍵は選挙の前に別の経路でも公開し、検証者は `--public-key` で固定する | 選挙が `closed` になり、公開鍵を公表した後に消す（以後ブロックを作らない） |
| 再投票の鍵 `revote_key`（64 桁の hex） | api（slot の計算） | `secrets/revote_key` だけ（環境変数では渡せない） | 投票期間中は変えない（変えると、変更前に投票した有権者の slot が変わり、その人の再投票は 409 `revote_conflict` になり続ける）。選挙ごとに新しく作る | 締切の手続きの中で、sealer（memory モードは api 内蔵のスケジューラ）がファイルごと消し、`election_audit` に `revote_key_destroyed` を記録する（消せなければ `closed` に進まない）。バックアップに含めない |
| 管理用トークン `admin.token` | api の管理用リスナー・`scripts/election.sh` | `secrets/admin_token` / `APP__ADMIN__TOKEN` | いつでも。api を再起動し、操作する人に新しい値を渡す | 選挙の終了後に消す |

- 鍵の作り方の例: `(umask 077; od -An -tx1 -N32 /dev/urandom | tr -d ' \n' > secrets/<名前>)`。
- `scripts/dev_up.sh`・`scripts/sample_data.sh`・`app.env=dev` の `scripts/election.sh` は、指定が無ければ**開発用の固定値**
  （`scripts/lib/common.sh`）を使う。公開されている値なので、本番では必ず自分で作った値を渡す。
- credgen が出力する `secrets/credentials.csv` と、`out/sample/credentials_patterns.csv` は平文のパスワードを含む。郵送の準備・確認が
  済んだら安全に消す。

## データを書き換えるときの決まり

### 選挙データ（seed）は init の前にだけ編集する

`seed/<election_id>/` は、DB を初期化して api・sealer を初めて起動する（init）前にだけ編集する。init の後は、選挙の定義を
変えない（候補者の追加・削除・名前の変更、選挙区や名簿の変更を含む）。

init の時点の選挙定義（有権者名簿を除く）のハッシュは、ジェネシスブロックに入り、署名されて公開される（[ADR 0025](adr/0025-election-definition-hash.md)）。
init の後に seed を変える（候補者の名前の入れ替えを含む）と、api と sealer は起動を拒否し、`verify` は NG、`tally` は集計を中止する
（終了コード 3）。表計算ソフトで保存し直しただけ（行・列の順番や改行コードの違い）では食い違いにならない。
有権者名簿（voters.csv）はハッシュに含まれないので、init の後に変えても検出されない（`auth.mode=db` の名簿は、credgen で DB に
取り込んだ後は DB が正）。

### 設定のうち `open` で固定される項目

`vote.allow_blank`・`vote.allow_revote`・`vote.max_revotes` は、`open` に移った時点の値が DB に固定され、以後は設定を変えても使われない
（原則19。[configuration.md](configuration.md#変更できるタイミング)）。封印ルール（`seal.*`）は原則19 の対象だが固定は未実装なので、
投票期間中は変えない。`chain.reveal_ballots` も、投票期間中に `always` へ変えると締切前に票が公開されるので変えない。

### 認証情報の再発行

`credgen --reissue` で、登録済みの有権者に新しい ID とパスワードを発行する（古いものは直ちに使えなくなる）。内部の voter_id は
変えないので、投票済みの記録は保たれ、再発行しても 2 回目の投票はできない。DB の `credentials` を直接書き換えない。

### DB の票を直接書き換えない

`blocks`・`anchors`・`ballot_pool`・`participation` を CQL で直接書き換えると、`verify` と `tally` で検出される（票を変えれば Merkle 根と
ブロックのハッシュが一致しなくなり、ブロックを作り直せば署名とアンカーが合わなくなり、件数を変えれば投票済み記録との突合が合わなくなる）。
これは改ざん検知の仕組みそのもので、「直した」つもりの書き換えも改ざんとして扱われる。データを消したいときは `scripts/db_reset.sh` を使う。
`scripts/check/chain.sh#6` が、ブロックを書き換えると集計が拒否されることを確認している。

## 既知の限界

- **再投票の回数が外から見える**: 再投票を認める選挙では、票に slot と seq が入るので、締切後に公開された票から「ある slot が何回投票し直したか」
  が分かる（誰の slot かは、鍵を破棄した後は分からない）。投票期間中も、ブロックの票数・時刻の分布から、再投票の多さは推測できる。
- **締切前に revote_key が漏れた場合**: 漏らした相手が voter_id の一覧を持っていれば、各有権者の slot を計算でき、公開された票と突き合わせて
  **誰が誰に投票したかが分かる**（秘密投票が破れる）。さらに、漏洩後に破棄しても、手元に写しがあれば締切後も同じことができる。
  鍵は secrets/ にだけ置き、バックアップ・ログ・DB に出さない。漏洩が疑われたら、その選挙の再投票の秘密性は失われたものとして扱う。
- **E2E 検証可能性がない**: 有権者は、自分の票がチェーンに正しく入ったことを確かめられない（`ballot_id` を有権者に返さないため。返すと、
  それを見せて投票先を証明できてしまい、買収・強要に使える）。検証できるのは「封印後に書き換えられていないこと」と「投票済み記録と
  票の数が合うこと」まで。api（や運用者）が受け付けた時点で投票先をすり替えることは検出できない。
- ログイン失敗の回数制限・ロックアウトが無い（LB・WAF で行う。[architecture-scaling.md](architecture-scaling.md#l7-ロードバランサー)）。
- セッションをサーバ側で個別に失効できない（有効期限 `session.ttl_secs` まで有効。止めるには `session.secret` を変える）。
