# 0002: ハッシュチェーンの正規化エンコードと Merkle 木の設計

## 背景
投票の改ざんを検知するため、票をブロックにまとめてハッシュチェーンで連結する。
ハッシュ対象のバイト列がシリアライザの実装差や将来の変更で揺れると、検証が壊れる。
また、秘密投票の原則により、ブロックや票から投票者・到着時刻が推測できてはならない。

## 決定
- **正規化バイナリ**（固定長・ビッグエンディアン。serde / JSON は使わない）
  - 票 = `ballot_id(16) ‖ candidate_id(4)`（20 バイト）
  - ヘッダ = `version(2) ‖ height(8) ‖ prev_hash(32) ‖ merkle_root(32) ‖ ballot_count(4) ‖ sealed_at_minute(8)`（86 バイト）
  - `block_hash = SHA256("vote/block/v1" ‖ ヘッダ)`
- **Merkle 木**: 葉 `SHA256(0x00 ‖ 票)`、内部 `SHA256(0x01 ‖ 左 ‖ 右)`、空 `SHA256(0x02)`。
  要素数が奇数のときは末尾を複製せず上の段へ持ち上げる。包含証明は「兄弟ハッシュと位置（左右）」の列。
- **票の並び順**: `SHA256("vote/ballot-order/v1" ‖ ballot_id)` の昇順。到着順と無相関にする。
  同一 `ballot_id` は封印時に `DuplicateBallot` として拒否し、検証時は「昇順でない」として拒否する。
- **ジェネシス**: 高さ 0、`prev_hash` 全ゼロ、票 0 件、根は空木の根。
- **時刻**: ヘッダの `sealed_at_minute`（UNIX 分）のみ。票には時刻を持たせない。
- **署名**: `block_hash` への Ed25519 署名（`verify_strict`）。`Signer` / `Verifier` トレイトは
  生のバイト列だけを扱い、署名ライブラリの型を公開しない。
- **検証**: `verify_chain` は先頭から順に、位置・`prev_hash`・空ブロック・件数・並び順・Merkle 根・
  `block_hash` 再計算・署名の順で調べ、最初の不整合を `ChainError`（種別ごとに別バリアント、位置付き）で返す。
- **乱数の扱い**: domain は乱数に依存しない。`BallotId::from_random_bytes` と `Ed25519Signer::from_seed` は
  呼び出し側が用意したバイト列を受け取る。

## 理由
- 手組みの固定長エンコードは、バイト単位で仕様を固定でき、実装間でも再現できる。
- 葉と内部ノードでプレフィックスを分けると、内部ノードを葉として提示する第二原像攻撃を防げる。
- 奇数個の複製を行わないので、末尾の票を重複させた別の票列が同じ根になる衝突（CVE-2012-2459 型）が起きない。
- `ballot_id` のハッシュ順は、到着順・投票順の推測を防ぐ（原則3）。UUIDv4 なので `ballot_id` 自体も時刻を含まない。
- 空ブロックを検証で拒否するのは、0 件で封印すると到着時刻が漏れるため（原則9）。
- domain を IO・乱数から切り離すと、純粋関数として決定的にテストできる（原則5）。

## 代替案
- **serde_json 等で正規化**: キー順・数値表現の揺れがあり、原則4に反するため不採用。
- **奇数個の末尾を複製**: 実装は簡単だが、上記の衝突があるため不採用。
- **票バイト列全体のハッシュ順**: `ballot_id` が同じで候補者だけ異なる票（二重投票）が別位置に並び、
  重複の検出が難しくなるため、`ballot_id` のみをキーにした。
- **署名対象にヘッダ全体を渡す**: `block_hash` がヘッダを一意に束ねるため、署名対象は 32 バイトで足りる。
