# 0009: 独立した sealer・リース・アンカー・監査用の突合

> **改訂**（[ADR 0020](0020-seal-policy-min-ballots.md)）: アンカーの判定の間隔の設定は `seal.interval_secs` に改名した。SIGTERM では
> 票をフラッシュせず、リースの解放（と、変化があれば最終アンカー）だけを行う。

## 背景
Step 6 まで、sealer は api プロセス内のタスクだった。api を水平にスケールさせると sealer も複数になり、
同じシャードを複数のプロセスが封印しようとして競合する。また、各シャードのチェーンは独立していて、
「他のシャードの状態」や「過去のブロックの巻き戻し」を単独では示せない。participation（投票済みの記録）と
チェーンの整合も、機械的には確認できなかった。

## 決定
- **sealer を独立したバイナリにする**（`crates/sealer` の bin）。`STORAGE=scylla` の api は封印せず、ジェネシスも作らない。
  `STORAGE=memory` では、従来どおり api プロセス内のタスクとして動かす（リースなし。単一プロセスなので不要）。
- **`SHARD_COUNT`（既定 1）**。票の振り分けは `shard_for` = ドメイン分離した SHA-256(`ballot_id`) の先頭 8 バイト mod `SHARD_COUNT`
  （`voter_id` からは決めない。秘密投票のため）。api と sealer で食い違うと、担当のいないシャードに票が入り封印されないので、
  DB の `cluster_config` に最初の値を登録し、一致しないプロセスは起動を拒否する。
- **リース**（`sealer_lease`。`shard-<n>` と `anchor`）:
  - 取得は `INSERT IF NOT EXISTS USING TTL`、更新は `UPDATE USING TTL ... IF owner = ?`（TTL の 1/3 ごと）、
    解放は `DELETE IF owner = ?`（正常停止時のみ）。
  - **リースを失ったら、そのシャードの処理を直ちに止める**。(a) 更新の LWT が不適用なら破棄する。(b) 更新が通らない場合に備え、
    保持してよい期限を単調時計で持つ（更新リクエストを出した時刻 + TTL − TTL/3）。**ブロックを `commit` する直前に必ず期限を確認**し、
    切れていれば何も書かない（票はプールに残る）。
  - 新規取得は 1 周期（TTL/3）に 1 シャードまで。同時に起動した複数の sealer の担当がおおむね分かれる。負荷の再分散はしない。
  - 取得した直後に、`recover`（前の保持者が `commit` の途中で落ちた場合の後始末）、ジェネシスの作成、封印窓のリセットを行う。
  - 保持者が落ちると、TTL で失効し、別の sealer が引き継ぐ。正常停止では、フラッシュしてからリースを解放する。
- **分岐しないことの保証**: ブロックの追加は `INSERT IF NOT EXISTS`（主キーは `shard, height`）なので、同じ高さに 2 つ目のブロックは置けない。
  競り負けた（`Conflict`）sealer は、`recover` して次の周期に持ち越す。
- **署名鍵の一貫性**: sealer は起動時に公開鍵を `signer_keys` に登録する（`INSERT IF NOT EXISTS`）。別の鍵が登録済みなら起動を拒否する。
  1 本のチェーンに別の鍵の署名が混ざるのを防ぐ。api は公開鍵を DB から読むため、**署名鍵の種（秘密）を持たない**。
- **アンカー**（`anchors`）: 全シャードの head（shard, height, block_hash）をまとめ、
  `SHA256("vote/anchor/v1" ‖ seq ‖ 分 ‖ prev_anchor_hash ‖ head 数 ‖ 各 head（shard 昇順、固定長ビッグエンディアン）)` を署名する。
  直前のアンカーのハッシュも含めるので、アンカー自身も鎖になる。`anchor` リースの保持者だけが、`SEAL_MAX_INTERVAL_SECS`
  （既定 600 秒 = 10 分）ごとに作る。`seq = 最新 + 1` を `INSERT IF NOT EXISTS` で書き、競り負けたら諦める。
  全シャードに head が揃うまでは作らない。変化がなくても間隔ごとに作る（生存の証跡）。ログと `GET /api/v1/anchors/latest` に出す。
- **監査用の突合**（`GET /api/v1/audit/counts` と `verifier verify`）: participation と票を票ごとに結び付けることはできない（秘密投票）ので、
  **コンテスト別の件数だけ**を比べる。`participation == チェーン内の票数 + 封印待ち` が各コンテストで成り立つこと、
  `ballot_id` がシャードをまたいで一意であること（二重封印の検出）、最新アンカーの署名・ハッシュと、その各 head が今のチェーンの
  ブロックと一致すること（巻き戻し・差し替えの検出）を確認する。

## 理由
- リースは「同時に 1 つのプロセスだけが担当する」ことを、DB の LWT だけで（別の調停サービスなしで）実現できる。
- 期限の確認を `commit` の直前に置くと、停止・分断から復帰した古い sealer が書き込まない。それでも書き込みが競合した場合の
  最後の砦が、`shard, height` の LWT による一意性。
- アンカーは、シャードごとの独立したチェーンを 1 つの署名済みのハッシュに束ねる。外部に出しておけば、後から「この時点でこの状態だった」
  を示せ、チェーンの巻き戻しや一部のシャードの差し替えを検出できる。
- 突合をコンテスト別の件数に限ると、投票者と票を結び付けずに、票の消失や水増しを検出できる。

## 代替案
- **リースの世代番号（フェンシングトークン）をブロックの書き込みの条件にする**: 古い sealer の書き込みを DB 側で確実に拒否できるが、
  Cassandra 系の LWT バッチは同じパーティション内でしか使えない。リースをブロックと同じパーティションに置く設計変更が要る。将来の課題。
- **シャードの担当をあらかじめ静的に割り当てる（sealer 番号 mod N）**: 単純だが、1 つが落ちたときに引き継げない。
- **メンバー管理（ハートビート）による均等な再分散**: 担当が偏らないが、テーブルとロジックが増える。今回は 1 周期 1 シャードの取得で代用。

## 既知の制限
- リースの期限確認から `commit` の完了までに、TTL/3 を超える遅延（DB の停止など）が起きると、古い sealer と新しい保持者が同じ票を
  別のブロックに封印する（二重封印）余地がある。発生しても `verifier verify` の `ballot_id` の重複検出で見つかる。
  根本対策は、上記の世代番号による DB 側の拒否。
- リースの期限はサーバ側の時計、確認は各 sealer の単調時計で行う。TTL/3 の余裕（時計の誤差・処理の遅れ）で吸収する前提。
- `audit_counts` は participation とプールを全体走査する（非ページング）。監査用の低頻度の呼び出しを想定しており、
  大規模なデータでは分割して読む実装への変更が要る。集計値の取得中に投票・封印が進むと、一時的に不一致に見えることがある
  （静止状態で確認する）。
- 新しい sealer を後から起動しても、既存の担当は再分散されない（空いたシャードだけを取る）。
- 今回の検証は Cassandra 5.0 で行った（ADR 0008）。ScyllaDB での LWT・TTL の挙動は未確認。
