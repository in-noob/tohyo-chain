# 0012: データに更新がない場合は、ブロックチェーンに何も追加しない（アンカーも）

## 背景
ブロックは、未封印の票が 0 件のまま窓が満了した場合も、0 件で締切フラッシュした場合も作らない（原則 9。到着時刻の
漏洩を防ぐ）。一方、アンカー（全シャードの head を署名でまとめたもの。ADR 0009）は、`seal.max_interval_secs` ごとに、
変化がなくても必ず作っていた。票が来ない間も、内容の同じアンカー（署名と通し番号、作成時刻だけが違う）が積み上がり、
公開ログと DB のアンカーが無意味に増える。また、アンカーの作成時刻から、票の有無（活動の有無）が読み取れる。

## 決定
- **アンカーは、変化があったときだけ作る**: `domain::anchor::compare_heads(直前のアンカー, 現在の head)` が
  `Unchanged` / `Advanced` / `Inconsistent` を返す純粋関数。`Advanced`（いずれかのシャードの高さが進んだ）のときだけ作る。
  `Unchanged` なら作らず、DEBUG ログに `skip` と出す。
- **アンカーを作る間隔のタイマーは、作らなくても進む**（`AnchorSchedule::due` が期限のたびに次の期限を進める）。
  判定は、期限ごとに 1 回。ブロックが封印された直後に期限が過ぎたときは、アンカーは最大 1 間隔遅れて作られる。
- **まだ 1 つもアンカーが無いとき**の基準は、ジェネシスだけの状態（全シャードの高さ 0）。つまり、最初の票が封印されるまで、
  初回のアンカーも作らない（ジェネシスだけの状態は「更新なし」）。
- **`Inconsistent`**（高さが戻った、同じ高さでハッシュが違う、シャードの構成が違う）は、チェーンの巻き戻し・分岐の
  疑いなので、新しいアンカーで上書きせず、`SealerError::AnchorInconsistent` として、エラーログに出す。
- **締切・停止時の最終アンカー**: `Sealer::finalize_anchor` を、停止時のフラッシュの後に呼ぶ（メモリ保存の runner と、
  `Coordinator::shutdown` のアンカー担当）。変化がなければ、最後のアンカーが最新の状態を指していることを**確認するだけ**で、
  作らない（`FinalAnchor::UpToDate`）。変化があれば、最後のアンカーを追いつかせるために 1 つ作る（`Created`）。
  投票期間（締切）は未実装なので、今ある「残りをすべて封印するフラッシュ」は停止時だけ。締切を実装するときは、
  同じ関数を、締切のフラッシュの後に呼ぶ。
- **ブロックの回帰テスト**: 0 件の窓の満了を何度繰り返しても、0 件の締切フラッシュ・停止でも、ブロックもアンカーも
  増えないことを、`sealer` のテスト（メモリ保存・時計を手動で進める）と `check_step10.sh`（実サーバ）で固定する。

## 理由
- 「データに更新がない場合は、何も追加しない」を、ブロックとアンカーの両方で一貫させる。公開ログ・DB・監査の対象が、
  実際の更新だけになる。
- アンカーの数が、票の活動と無関係な時刻の刻みに比例しなくなる（活動の有無が、作成時刻から読み取れなくなる）。
- 変化の判定を純粋関数にすれば、時計もストアも使わずに、網羅的に単体テストできる。

## 代替案
- **初回だけは、ジェネシスを固定するアンカーを作る**: ジェネシスは、最初のブロックとして、各シャードの先頭から
  検証できる。「更新なし」で何も作らない方針と食い違うので、採らなかった。
- **変化を検知した時点で、すぐにアンカーを作る（間隔を待たない）**: アンカーの作成頻度が、封印の頻度と同じになり、
  間隔（`seal.max_interval_secs`）で作成頻度を抑える設計と食い違う。採らなかった。
- **締切・停止時の最終アンカーを、常に作る**: 変化がなければ、内容の同じアンカーが増えるだけ。採らなかった。
