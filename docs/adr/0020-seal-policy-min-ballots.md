# 0020: 封印ルールの改定（最小件数・投票開始からの経過時間・締切の手続きだけのフラッシュ）

ADR 0003（封印ポリシーの純粋関数化）の判定ルールと、ADR 0005・0012・0016 のうち「停止時（SIGTERM）に残りを封印する」
部分を置き換える。純粋関数で時刻を引数に取る方針（0003）はそのまま。

## 背景
原則9 を次のように改めた。

- 未封印が `seal.max_ballots`（100）件に達したら、100 件ですぐに封印する（変更なし）。
- 前回の封印（**または投票開始**）から `seal.interval_secs`（600）秒以上経ち、**かつ未封印が
  `seal.min_ballots_after_interval`（10）件以上**なら、全件を封印する。
- 上の 2 つに当てはまらなければ待つ。**0 件のときも待ち、窓のリセットはしない**。
- 投票終了の手続きの中でだけ、残りを件数に関係なく封印する。**SIGTERM で停止するときはフラッシュしない**。

旧ルールには、次の問題があった。

- 1 件でも時間で封印するので、票の少ないシャード（深夜など）では 1〜数票のブロックができる。票の並べ替え（原則3）をしても、
  1 票のブロックは「その 10 分間の票」を特定しやすい（秘密投票の弱まり）。
- 0 件で窓が満了すると窓をリセットしていたので、窓の起点が「前回の封印」ではなくなり、ルールの説明と実装が食い違っていた。
- 停止（SIGTERM）のたびに端数が封印され、ブロックの大きさと時刻が、運用操作（再起動・デプロイ）に左右された。

## 決定
- `domain::seal_policy`（純粋関数。時刻は UNIX 秒の引数）:
  - 設定は `SealPolicy { max_ballots, interval_secs, min_ballots_after_interval }`（どれも 1 以上。`new` で検証）。
  - 判定結果は `SealCount(max_ballots)` / `SealAll` / `Wait` / `CloseFlush` の 4 つ。`ResetWindowOnly` は削除した
    （0 件は `Wait`。窓をリセットしない）。
  - `window_start(last_sealed_at, voting_started_at) = max(前回の封印時刻, 投票開始時刻)`。まだ封印していなければ投票開始時刻。
  - `decide(pending, window_start, now, policy)`: 投票期間中の判定（件数が最優先。次に「経過 >= interval かつ
    件数 >= 最小件数」で `SealAll`。それ以外は `Wait`。境界はどちらも「以上」）。
  - `decide_close(pending, policy)`: 締切の手続きの中の判定。`max_ballots` 件以上なら `SealCount`、1 件以上なら
    `CloseFlush`、0 件なら `Wait`。250 件なら 100（count）・100（count）・50（close）の 3 ブロック（1 ブロックの上限を守る）。
  - 最小件数 > 最大件数は拒否しない（件数による封印が常に先に起きるので、時間では封印されないだけ。確認用に
    `max_ballots` だけを小さくする設定を許すため）。
- **投票開始時刻**: 選挙状態（ADR 0019）に `opened_at`（open に遷移した時刻。DB の `election_state.opened_at` 列）を追加し、
  `domain::voting_started_at(period, opened_at) = max(opened_at, period.opens_at)` とする。票を受け付けるのは
  「open かつ 開始時刻 <= 現在時刻」（原則18）なので、実際に票が入り始めるのは、この 2 つの遅い方。開始前に投入された票は
  ない前提。sealer（runner・Coordinator）は、周期ごとに選挙状態を読み、`Sealer::set_voting_started_at` に渡す。
  選挙状態を使わない実行（テスト）では、シャードを担当し始めた時刻で代用する。
- **時計**: 封印の経過時間は、壁時計（UNIX 秒）で測る。投票開始時刻が DB に記録された壁時計の時刻なので、同じ時計で比べる
  必要があるため（旧実装は単調時計の `Duration`）。秒の精度になる（最大 1 秒未満、早く判定されうる。600 秒の間隔に対しては
  無視できると判断した）。リース・アンカーの周期・締切の待ち時間は、引き続き単調時計で測る。
- **前回の封印時刻**: 同じプロセスで封印した場合は、その時刻（メモリ）。リースの引き継ぎ・再起動の後は、チェーンの先頭ブロック
  （票を含むもの）の `sealed_at_minute` から、**その分の最後の秒**（`分 * 60 + 59`）とみなす。実際より遅い側に寄せることで、
  `interval_secs` より早く時間で封印することはない（遅れは最大 59 秒）。
- **フラッシュ**: `Sealer::close_flush`（`decide_close`）は、選挙状態が `closing` の間（締切の手続き）にだけ呼ぶ
  （memory: runner の `election_tick`、db: `Coordinator` の `close_flush_held`）。停止（`SealerHandle::shutdown` /
  `Coordinator::shutdown`）では呼ばない。未封印の票は、DB モードではストアに残り、引き継いだ sealer が封印ルールに従って
  封印する（memory モードでは、プロセスの終了とともに消える。memory は開発用）。
- **停止時の最終アンカー**: 残す。フラッシュはしないが、最後のアンカー以降に増えたブロックがあれば、それをアンカーに含める
  （変化がなければ作らない。ADR 0012 のまま）。
- **ログの trigger**: `count | time | close` の 3 種類（`flush` を `close` に改名）。
- **設定**: `seal.max_interval_secs` を `seal.interval_secs` に改名し、`seal.min_ballots_after_interval`（既定 10）を追加。
  古い名前は、未知の項目としてエラーになる（タイプミスの検出と同じ仕組み）。`config/dev.toml` は interval=10 秒・min=10。

## 理由
- 最小件数を設けることで、時間による封印でも、1 ブロックに最低 10 票が入る（原則9 の目的: ブロックから票の到着時刻を
  推測しにくくする）。端数は締切の手続きでまとめて封印されるので、票が失われることはない。
- 起点を max(前回の封印, 投票開始) にすることで、「投票開始から 10 分経つまでは、時間では封印しない」がルールどおりになる
  （sealer の起動時刻や、開始前の待機時間に左右されない）。
- 窓をリセットしないことで、「10 件目が届いた時点で、前回の封印から 10 分以上経っていれば、すぐに封印する」が成り立つ
  （リセットすると、10 件目から更に最大 10 分待つことになる）。
- 停止でフラッシュしないことで、運用操作（再起動・デプロイ・スケールイン）がブロックの形に影響しない。締切の手続き
  （ADR 0019）は、全シャードのフラッシュと「未封印 0 件」の確認をするので、最終結果の完全性は変わらない。
- `opened_at` を記録するのは、`open --now`（手動）や、期間未設定で開けた場合にも、投票開始時刻を 1 つに決めるため。

## 代替案
- **投票開始時刻を設定の `voting_opens_at` だけにする**: スキーマは変わらないが、期間未設定で `open --now` した場合に起点が
  無くなり、sealer が open を観測した時刻（プロセスごと・再起動で失われる）で代用することになる。DB を正とする原則17 に
  合わせ、遷移時刻を記録する方を採った（既存の開発用キースペースは `scripts/db_reset.sh --all` が必要）。
- **引き継ぎ後の前回の封印時刻に、先頭ブロックの分の最初の秒を使う**: 最大 59 秒早く時間で封印してしまう（ルール違反）。
  「引き継いだ時刻」を使う案は、クラッシュからの引き継ぎで、リースの TTL 分だけ遅れ、DB を正としない。分の最後の秒を採った。
- **締切の手続きで、250 件をすべて trigger=close にする**: 100 件のブロックは件数による封印と区別できなくなる利点はあるが、
  判定の型（4 種類）とログのきっかけが一対一に対応しなくなるため、count・count・close にした。
- **停止時の最終アンカーも作らない**: 停止時の後始末が「リースの解放」だけになり単純だが、最後のアンカー以降に増えたブロックが、
  次のアンカーまで（引き継ぐ sealer が作るまで）アンカーで守られない。変化があるときだけ 1 つ作る方を採った。
