# 0025: 選挙定義のハッシュをブロックヘッダーに入れる（ブロックの形式の版 4）

## 背景
- 票には候補者の ID（`candidate_id`）だけが入り、候補者の名前・政党などは、集計（`verifier tally`）のときに手元の seed から引く。
- これまでのジェネシスブロックは、高さ・前のハッシュ・空の Merkle 根・時刻だけで、選挙定義を何も表していなかった。そのため、init
  （DB を作って api・sealer を初めて起動する）の後に seed の候補者名を入れ替えても、`verify` は OK のまま、集計結果の名前だけが
  黙ってすり替わった（票の ID はそのまま通るので、`tally` も中止しない）。
- ジェネシスを作るのは sealer（`Sealer::init_shard`）で、シャードのリースを取った後に遅れて作る。db モードの api は、sealer が
  ジェネシスを作る前に起動することがある。
- 候補者の表示順は、これまで CSV の行の順番だった。行を並べ替えるだけで、投票用紙の候補者の並び（順序効果のある、選挙定義の一部）が
  変わった。

## 決定
- **ハッシュの対象**: seed から読み込んで検証した後の選挙定義（`domain::Election`）を、`domain::election_definition_hash` で
  固定長ビッグエンディアンのバイナリに正規化して SHA-256 を取る（原則4。serde_json は使わない）。
  ```text
  SHA256("vote/election-definition/v1"
         ‖ str(election_id) ‖ str(name)
         ‖ u32(種類の数)   ‖ 種類ごと（code 順）:   str(code) ‖ str(name) ‖ u32(order) ‖ str(method)
         ‖ u32(選挙区の数) ‖ 選挙区ごと（ID 順）:   str(id) ‖ str(election_type) ‖ str(name)
                                                   ‖ u32(都道府県の数) ‖ str(都道府県)…（コード順） ‖ u32(order)
         ‖ u32(候補者の数) ‖ 候補者ごと（選挙区 ID 順、次に連番の数値順）: str(id) ‖ str(name) ‖ str(party) ‖ str(profile))
  str(s) = u32(UTF-8 のバイト数) ‖ UTF-8 のバイト列
  ```
  - ID・コード順に並べ直すので、ファイルの行の順番・CSV の列の順番・election.toml の `[[types]]` の順番が違っても、同じ内容なら
    同じハッシュになる。改行コードは、seed の読み込みで、値の中の CRLF・CR を LF にそろえる（セル内の改行を含む）。
  - 有権者名簿（voters.csv）は含めない。
- **候補者の表示順**: 選挙区の中では、候補者コードの連番（`c{連番}`）の数値順にする（行の順番に依存させない）。並び順を変えるには ID を
  変えるしかなく、ID はハッシュに入るので、並び順のすり替えも検出できる。
- **置き場所**: `BlockHeader` の末尾に `election_hash`（32 バイト）を足し、`BLOCK_VERSION` を 4 にする（ヘッダーは 86 → 118 バイト）。
  ジェネシスが値を持ち（`domain::genesis(signer, 分, election_hash)`）、`seal_block` は前のブロックの値を引き継ぐ。`verify_chain` は、
  全ブロックの値がジェネシスと同じことを確認する（違えば `ChainError::ElectionHashMismatch`）。値は `block_hash` の対象なので、
  書き換えればブロックのハッシュと署名も合わなくなる。
- **起動時の照合**: api と sealer は、起動時に手元の seed のハッシュを計算し、次の順で照合する。
  1. 既にあるチェーンの先頭ブロック（ジェネシスから値を引き継いでいる）と比べ、違えば起動を拒否する（memory モードはこれだけ。
     sealer は `Sealer::check_existing_chains`。リースを取った後の `init_shard` でも確かめるが、そこでの失敗はリースを返して続けるだけなので、
     起動時に止める）。
  2. db モードでは `cluster_config` の `election_hash` 行に LWT（`IF NOT EXISTS`）で登録し、登録済みの値と違えば起動を拒否する
     （`shard.count` と同じ仕組み。先に起動した側が値を決めるので、ジェネシスがまだ無くても、起動の順番に関係なく検出できる）。
     1 の後に行うので、チェーンと食い違う値を登録してしまうことはない。
  - エラーには、理由と直し方（seed を init の時点の内容に戻すか、`scripts/db_reset.sh --all` で作り直す）を出す。
  `db_reset.sh --votes` は `cluster_config` を残すので、選挙定義を変えるには `--all` が要る。
- **verifier**: `verify` と `tally` は、手元の seed（設定の `election.seed_dir` / `election.election_id`）のハッシュと、全シャードの
  ジェネシスの値を照合する。シャードの間で値が違うか、手元の seed と違えば NG（終了コード 3）。seed を読めなければ実行時のエラー（1）。
- **公開**: `GET /api/v1/election-status` とチェーンの API のヘッダーに `election_hash`（64 桁の hex）を足し、ビューア（/chain と
  ブロックの詳細）に表示する（呼び名は `labels.election_hash`。原則12）。
- **スキーマ**: `blocks` に `election_hash blob` の列を足す。列の無い古いスキーマは、接続時に `scripts/db_reset.sh --all` の手順つきで拒否する。

## 理由
- 集計の表示名は seed から引くので、seed の内容そのものを、署名つきのチェーンに固定するのがいちばん直接的。ヘッダーに入れれば、既存の
  「ブロックのハッシュ → 署名 → アンカー」の検証にそのまま乗る。
- 読み込んだ後の値を正規化してハッシュするので、表計算ソフトで保存し直した（行・列の順番や改行コードが変わった）だけで食い違いにならない。
  一方、名前を 1 文字変えれば必ず変わる。
- 起動時に拒否すれば、違う seed のまま投票を受け付けたり、封印したりすることがない。`cluster_config` への登録は、ジェネシスが
  まだ無い時点で起動した api も止めるため。改ざんの検出そのものは、公開 API だけで確かめられるジェネシスの値で完結する。

## 代替案
- **ファイルのバイト列のハッシュ**: 表計算ソフトで開いて保存し直すだけ（改行コード・列の順番・行の順番・末尾の空行）で値が変わり、
  内容が同じでも食い違いになる。どのファイルを含めるか（voters.csv やコメント）もあいまいになる。却下。
- **ジェネシスだけに入れる**: 途中のブロックは値を持たないので、ブロックを 1 つ見ただけでは、どの選挙のものか分からない。
  ヘッダーの形が高さで変わると、エンコードと検証が場合分けになる。32 バイトの増加は小さいので、全ブロックに入れる。
- **ジェネシスの Merkle 根の欄を流用**: 票の Merkle 根という意味と混ざり、「ジェネシスの Merkle 根は空の根」という既存の検証を
  崩す。途中のブロックでは使えない。却下。
- **アンカーに入れる**: アンカーは定期的に作られる後付けの記録で、最初のアンカーまでの間は固定されない。ブロックだけを見る
  検証者は照合できない。却下。
- **名簿（voters.csv）も含める**: 名簿は有権者の ID を含み、ハッシュを公開しても推測の手掛かりになり得る。db モードの名簿は
  credgen で DB（`voter_roll`）に取り込んだ後は DB が正で、seed のファイルと一致し続ける保証もない。集計の表示名にも関わらない。却下。
- **食い違いは警告だけ**: 警告は見落とされる。違う候補者名のまま投票を受け付けたり集計したりすると、取り返しがつかない。
  `shard.count` の食い違いと同じく、起動を拒否する。却下。
