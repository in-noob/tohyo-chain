# 0006: 画面（Leptos CSR）の構成と秘密投票への配慮

## 背景
Step 5 で、Step 4 の API（`STORAGE=memory`）に接続する投票画面を実装する。
画面は投票者の操作を扱うため、秘密投票（原則1）とセッション（原則6）に配慮した作りが必要になる。

## 決定
- **構成**: `crates/web`（lib + wasm 用 bin）。Leptos 0.8 系の CSR、`leptos_router`、Trunk。
  依存してよいワークスペースクレートは `shared-types` のみ（原則5）。
- **画面遷移のロジックは `flow` モジュールの純粋関数**に置く（次の未投票コンテスト、ルート保護、
  投票画面の状態遷移、API 結果の分類、入力検証）。Leptos・ブラウザ API に依存しないので、
  wasm-bindgen-test なしの通常の `cargo test` で検証できる。UI は `flow` の返す値に従うだけにする。
- **セッショントークンはメモリ（シグナル）にだけ保持**する。localStorage / sessionStorage / Cookie には保存しない。
  リロードで再ログインが必要になるが、共用端末にトークンが残らない。
- **候補者は投票画面の中（`VotePhase`）にだけ持つ**。URL・履歴・共有状態・ログ・ストレージに置かない。
  送信が終わって画面を離れるときに段階を初期化して捨てる。完了画面への遷移は履歴を置き換え（`replace`）、
  戻るボタンで投票画面に戻れないようにする。
- **完了画面は「投票を受け付けました」のみ**（`flow::DONE_MESSAGE`）。票がサーバに受理されたことだけを示し、
  ブロックの封印・検証とは無関係であることをコードのコメントに明記する。候補者名・`ballot_id` は出さない。
  操作ボタン（次のコンテストへ / 終了）は投票内容を示さない。
- **確認ステップ**を設け、送信前に選んだ候補者名を表示する（誤投票の防止）。候補者名を表示するのはここまで。
- **ルート保護は、ログイン状態だけを追跡して判定**する。投票受理による一覧の更新で再判定すると、
  完了画面への遷移と競合して意図しないリダイレクトが起きるため。
- **開発時の接続**: `trunk serve`（ポート 8080）が `/api` を `http://localhost:18080/api/` へそのまま転送する（api は `API_PORT=18080` で起動する。`scripts/dev_up.sh` の構成）。
  画面から見ると同一オリジンで、CORS は不要。API のオリジンは成果物に焼き込まず、相対パスで呼ぶ。
- **リリースのサイズ**: ルートの `[profile.release]` を `opt-level = "z"`、`lto = true`、`codegen-units = 1` にする
  （wasm の配布サイズのため。API などの release ビルドにも適用される）。

## 理由
- 純粋関数に切り出すと、遷移の網羅的なテストがブラウザなしで書け、UI の変更に強い。
- トークンをメモリだけに持つと、盗まれる面が減る。投票所の共用端末を想定するとリロードでの再ログインは許容できる。
- 候補者を残さない設計は、画面側の不具合や利用者の履歴閲覧から投票内容が推測されるのを防ぐ。

## 代替案
- **トークンを sessionStorage に保存**: リロードに耐えるが、同一オリジンのスクリプトから読めてしまう。不採用。
- **選択中の候補者を URL に含める（`/contests/1?candidate=101`）**: 共有・履歴に残るため不採用。
- **完了画面に投票内容の確認を表示**: 買収・強要の証拠になり得るため不採用（サーバもレシートを返さない）。
- **UI の遷移をコンポーネント内に直接書く**: ブラウザでしか検証できず、回帰しやすいため不採用。

## 留意点
- 画面の見た目・操作・DevTools での秘密投票の確認は自動化していない。`docs/manual_check_step5.md` の手動確認で行う。
- 静的ホスティングでは、`/contests/1` などの URL が `index.html` に解決される SPA フォールバックが必要
  （`trunk serve` は既定で対応している）。
- 国民審査は、他のコンテストと同じ「候補者を 1 人選ぶ」形式に単純化している（ADR 0004）。
